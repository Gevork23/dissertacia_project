# ДГТУ — интеллектуальная система анализа нормативно-правовых документов

## О проекте

Проект разрабатывается как магистерская работа и как прикладной инструмент для использования в МФЦ Ростовской области.

Базовая формулировка проекта:

**Интеллектуальная система анализа нормативно-правовых документов, обеспечивающая выявление значимых изменений, генерацию кратких разъяснений и формирование адаптивных тестовых материалов для проверки знаний сотрудников.**

Ключевая идея проекта — не общий чат по законам и не абстрактный поиск по нормативной базе, а **прикладной конвейер работы с версиями одного документа**:

**документ → версии → изменения → выжимка → генерация теста → прохождение теста → отчёт**

## Зачем создаётся проект

1. Как сильный магистерский проект для защиты в ДГТУ.
2. Как прикладной инструмент для использования в МФЦ Ростовской области.
3. Как демонстрируемая локальная система, которую можно развернуть на одном ПК и показать комиссии в живом сценарии.

## Главный режим анализа

Главный режим проекта:

**сравнение новой редакции документа с предыдущей редакцией того же документа**

Это означает, что ядро системы должно обеспечивать:

- загрузку документа;
- хранение нескольких редакций;
- разбиение текста на структурные фрагменты;
- сравнение двух версий;
- выделение значимых изменений;
- формирование краткой выжимки;
- генерацию тестовых материалов по изменениям;
- прохождение теста сотрудником;
- сохранение результатов и формирование отчёта.

## Что входит в MVP

В MVP должны входить:

- загрузка документов;
- загрузка новых версий документов;
- парсинг DOCX / PDF / TXT;
- разбиение на статьи / пункты / подпункты;
- сравнение двух редакций одного документа;
- выявление изменений;
- краткая выжимка по изменениям;
- генерация теста;
- утверждение теста ответственным лицом;
- прохождение теста сотрудником с указанием ФИО;
- сохранение результатов;
- отчёты;
- стабильный запуск;
- автотесты.

## Что не является ядром MVP

Ниже перечислены функции, которые допустимы, но не должны размывать основной сценарий:

- чат по документам;
- сложный глобальный поиск по большой нормативной базе;
- тяжёлые внешние интеграции;
- сложные личные кабинеты;
- “AI-функции ради AI-функций”.

## Текущее состояние репозитория

Текущая версия репозитория уже ориентирована на демонстрационный MVP и защиту. В проекте есть:

- модели документов, версий, чанков, тестов и попыток;
- загрузка TXT / DOCX / PDF;
- автоматическое извлечение текста и построение чанков после загрузки версии;
- API для сравнения версий, краткой выжимки, генерации теста, утверждения теста и отчёта;
- demo-corpus и команда его загрузки;
- минимальный demo UI на Django templates;
- автотесты для backend и demo-потока;
- локальное развёртывание через Docker Compose.

Репозиторий доведён до состояния, в котором можно показать полный цикл:

**документ → версии → изменения → выжимка → тест → утверждение → прохождение → отчёт**

## Архитектурная идея

Система проектируется как локально разворачиваемое веб-приложение с доступом по сети внутри организации.

Высокоуровневая схема:

- тонкий веб-интерфейс для демонстрации и работы пользователей;
- backend-приложение с бизнес-логикой;
- база данных для хранения документов, версий, тестов и результатов;
- файловое хранилище для загруженных исходников;
- вспомогательные AI-компоненты для анализа текста, если они усиливают основной сценарий, а не подменяют его.

- `backend/` — серверная часть проекта
- `docs/` — проектные заметки и сценарии демонстрации
- `data/` — вспомогательные наборы данных
- `tools/` — утилиты для подготовки и оценки данных
- `infra/` — переменные окружения и инфраструктурные заготовки

## Принцип развития проекта

Если какая-либо функция, документ, архитектурное решение или AI-механика:

- не усиливают главный сценарий;
- мешают срокам;
- усложняют демонстрацию;
- не поддерживают прикладную ценность для МФЦ;

то такие элементы должны быть упрощены, отложены или исключены из MVP.

## Быстрый старт

1. Скопируйте пример переменных окружения:

```bash
cp infra/.env.example infra/.env
```

2. Соберите и поднимите сервисы:

```bash
docker compose up --build
```

3. Проверьте доступность backend health endpoint:

```bash
docker compose ps
curl http://localhost:8000/api/health
```

4. Проверьте доступность Qdrant:

```bash
curl http://localhost:6333/collections
```

5. Загрузите демонстрационный набор:

```bash
docker compose exec backend python manage.py load_demo_pairs
```

6. Откройте demo UI:

```bash
http://localhost:8000/
```

7. При необходимости откройте логи:

```bash
docker compose logs -f backend
docker compose logs -f db
docker compose logs -f qdrant
```
8. Остановка:

```bash
docker compose down
```

9. Полный сброс:

```bash
docker compose down -v
```
