# Demo Corpus Description

## 1. Назначение demo corpus

Demo corpus подготовлен для Фазы 12 как небольшой, воспроизводимый и понятный набор синтетических документов, на котором можно показать полный MVP pipeline проекта:

**document upload → document versioning → text extraction → normalization → structural chunking → version comparison → significance classification → summary → quiz generation → approval workflow → employee attempt → result/reporting.**

Корпус не предназначен для строгой экспериментальной оценки качества. Его задача — дать стабильный материал для демонстрации комиссии и объяснить, какие изменения специально заложены в каждой паре документов.

## 2. Принципы подготовки документов

Документы подготовлены как синтетические внутренние регламенты. Они юридически похожи на реальные регламентные документы, но не являются копиями законов, административных регламентов или внутренних документов организаций.

При подготовке соблюдены следующие принципы:

- все документы небольшие и читаемые;
- структура построена через разделы, статьи и пункты, чтобы поддержать rule-based structural chunking;
- каждая пара демонстрирует один основной тип изменения;
- тексты не содержат персональных данных, паспортных номеров, адресов, телефонов реальных лиц или секретной информации;
- metadata описывает ожидаемое demo-поведение, но не является экспертной разметкой для метрик.

## 3. Структура каталога

```text
data/demo_corpus/
    pair_01_deadline_change/
        old.txt
        new.txt
        metadata.json
    pair_02_added_clause/
        old.txt
        new.txt
        metadata.json
    pair_03_document_list_change/
        old.txt
        new.txt
        metadata.json
    pair_04_refusal_ground_change/
        old.txt
        new.txt
        metadata.json
    pair_05_editorial_changes/
        old.txt
        new.txt
        metadata.json
```

Используется формат TXT, потому что текущий ingestion pipeline стабильно поддерживает TXT, DOCX и PDF с текстовым слоем, а TXT минимизирует бинарные риски во время демонстрации и хорошо подходит для deterministic extraction/normalization/chunking.

## 4. Список пар документов

| Pair | Scenario | Main change | Expected significance | Demo value |
|---|---|---|---|---|
| `pair_01_deadline_change` | Изменение срока | Срок рассмотрения заявления изменён с 10 до 7 рабочих дней | `critical` в текущих правилах проекта | Лучший базовый кейс для показа compare → summary → quiz |
| `pair_02_added_clause` | Добавление нового пункта | Добавлен пункт об электронной подаче обращения через личный кабинет | `important` | Показывает added clause и процедурное изменение |
| `pair_03_document_list_change` | Изменение перечня документов | Добавлена копия документа, подтверждающего полномочия представителя | `critical` в текущих правилах проекта | Хороший кейс для вопроса в quiz по добавленному документу |
| `pair_04_refusal_ground_change` | Изменение основания отказа | Добавлено новое основание отказа: непредставление обязательных документов в срок | `critical` | Показывает наиболее чувствительное содержательное изменение |
| `pair_05_editorial_changes` | Редакционные изменения | Исправлены `е/ё` и пунктуация без изменения смысла | `editorial` | Показывает, что значимые изменения отделяются от редакционных |

## 5. Pair 01 — Deadline change

**Файлы:** `data/demo_corpus/pair_01_deadline_change/old.txt`, `new.txt`, `metadata.json`.

Сценарий показывает изменение срока рассмотрения заявления:

- старая редакция: срок составляет 10 рабочих дней;
- новая редакция: срок составляет 7 рабочих дней.

Ожидаемое поведение pipeline:

1. structural chunking выделяет пункт `Раздел 2, статья 2, пункт 1`;
2. comparison фиксирует `modified` fragment;
3. significance-layer относит изменение срока к наиболее значимым изменениям;
4. summary сообщает о сокращении срока;
5. quiz generation формирует вопрос о новом сроке рассмотрения заявления.

Эта пара рекомендуется как основной материал для 5-минутной демонстрации.

## 6. Pair 02 — Added clause

**Файлы:** `data/demo_corpus/pair_02_added_clause/old.txt`, `new.txt`, `metadata.json`.

Сценарий показывает добавление нового процедурного пункта:

- в новой редакции появляется пункт о возможности использовать электронную форму в личном кабинете заявителя на внутреннем портале.

Ожидаемое поведение pipeline:

1. comparison фиксирует добавленный пункт как `added`;
2. significance-layer относит изменение к процедурно значимым;
3. summary сообщает о новом способе подачи обращения;
4. quiz generation может сформировать вопрос о новой возможности подачи.

Эта пара удобна для объяснения added changes и процедурного эффекта изменения.

## 7. Pair 03 — Document list change

**Файлы:** `data/demo_corpus/pair_03_document_list_change/old.txt`, `new.txt`, `metadata.json`.

Сценарий показывает изменение перечня документов:

- в новой редакции к перечню добавлена копия документа, подтверждающего полномочия представителя.

Ожидаемое поведение pipeline:

1. comparison фиксирует изменение пункта с перечнем документов как `modified`;
2. significance-layer относит изменение перечня документов к ключевым изменениям;
3. summary сообщает о новом документе;
4. quiz generation формирует вопрос о том, какой документ добавлен.

Эта пара рекомендуется как второй основной кейс после Pair 01.

## 8. Pair 04 — Refusal ground change

**Файлы:** `data/demo_corpus/pair_04_refusal_ground_change/old.txt`, `new.txt`, `metadata.json`.

Сценарий показывает добавление нового основания отказа:

- в новой редакции добавлено основание отказа при непредставлении обязательных документов в установленный срок.

Ожидаемое поведение pipeline:

1. comparison фиксирует новый пункт как `added`;
2. significance-layer относит изменение к наиболее значимым, потому что оно влияет на условия отказа;
3. summary сообщает о новом основании отказа;
4. quiz generation формирует вопрос о новом основании отказа.

Эта пара хорошо подходит для демонстрации чувствительных юридически значимых изменений.

## 9. Pair 05 — Editorial changes

**Файлы:** `data/demo_corpus/pair_05_editorial_changes/old.txt`, `new.txt`, `metadata.json`.

Сценарий показывает редакционные изменения без существенного смысла:

- исправление `Прием` → `Приём`;
- удаление завершающей точки в одном пункте.

Ожидаемое поведение pipeline:

1. comparison может зафиксировать `modified` фрагменты;
2. significance-layer должен классифицировать их как `editorial`;
3. summary должен использовать editorial fallback и не раздувать изменения как содержательные;
4. saved quiz workflow не должен сохранять содержательный quiz для пары, где нет meaningful changes.

Эта пара нужна не для основного demo path, а для ответа на вопрос комиссии: как система ведёт себя на редакционных правках.

## 10. Как использовать corpus в demo

Из корня репозитория:

```bash
python backend/manage.py load_demo_corpus
```

Совместимый alias для существующих инструкций:

```bash
python backend/manage.py load_demo_pairs
```

Из каталога `backend/`:

```bash
python manage.py load_demo_corpus
```

Команда выполняет следующие действия:

1. читает `data/demo_corpus/`;
2. валидирует наличие `old.txt`, `new.txt` и `metadata.json`;
3. удаляет старые demo-документы с префиксом `DEMO МФЦ:`;
4. создаёт `Document` и две `DocumentVersion` для каждой пары;
5. запускает штатный ingestion для text materialization и structural chunks;
6. выводит id версий и URL для ручной проверки compare/brief/quiz.

Для проверки без записи в БД:

```bash
python backend/manage.py load_demo_corpus --dry-run
```

## 11. Recommended 5-minute demo path

Рекомендуемый быстрый сценарий:

1. Выполнить `python backend/manage.py load_demo_corpus`.
2. Открыть `/demo/`.
3. Выбрать `DEMO МФЦ: изменение срока рассмотрения заявления`.
4. Открыть сравнение версий `v1 → v2`.
5. Показать `modified` фрагмент со сроком `10 → 7 рабочих дней`.
6. Показать significance label и brief/summary.
7. Создать quiz по изменениям.
8. Отправить quiz на проверку и утвердить ответственным лицом.
9. Пройти quiz от имени сотрудника.
10. Открыть result/reporting.

Резервный второй кейс:

- `pair_03_document_list_change` — хорошо показывает изменение перечня документов и генерацию вопроса о добавленном документе;
- `pair_04_refusal_ground_change` — хорошо показывает критичное юридически значимое изменение.

Pair 05 стоит использовать только как отдельный короткий контрастный пример редакционных правок.

## 12. Ограничения

- Corpus является демонстрационным, а не evaluation corpus.
- Metadata описывает expected demo behavior, но не является ручной экспертной разметкой для precision/recall/F1.
- TXT выбран для стабильного локального demo; DOCX/PDF поддерживаются ingestion pipeline, но не нужны для этой фазы.
- Документы специально короткие, чтобы демонстрация была понятной и не перегружала UI.
- Corpus не проверяет OCR, RAG, внешние legal integrations, BI, LMS или production RBAC, потому что они вне MVP scope.

## 13. Связь с future evaluation corpus

Фаза 12 создаёт только demo corpus. Он нужен для красивой и стабильной демонстрации полного MVP pipeline.

Фаза 13 должна создавать отдельный evaluation corpus, если потребуется строгая экспериментальная проверка. В evaluation corpus могут появиться отдельные annotation files, метрики и протоколы оценки, но они не входят в текущую фазу.

## 14. Вывод

Demo corpus Фазы 12 закрывает задачу демонстрации полного локального цикла:

**версия документа → анализ изменений → выжимка → тест → утверждение → прохождение → результат.**

Корпус состоит из пяти синтетических пар документов, каждая из которых показывает отдельный тип изменения. Материалы безопасны для публикации в репозитории, не содержат персональных данных и не копируют реальные нормативные документы.
