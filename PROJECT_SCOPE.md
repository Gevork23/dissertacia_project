# PROJECT_SCOPE

## 1. Цель проекта

Создать интеллектуальную систему анализа нормативно-правовых документов, которая помогает быстро и понятно объяснять сотрудникам, что изменилось в новой редакции документа, и проверять усвоение изменений через тестирование.

## 2. Основной прикладной сценарий

Главный сценарий проекта:

**документ → версии → изменения → выжимка → генерация теста → прохождение теста → отчёт**

Это и есть ядро MVP.

## 3. Основной режим анализа

Основной режим анализа:

**сравнение новой редакции документа с предыдущей редакцией того же документа**

Проект не должен терять этот фокус.

## 4. Пользовательские роли MVP

В MVP достаточно следующих ролей:

### 4.1. Администратор / оператор
Отвечает за:

- загрузку документа;
- загрузку новых редакций;
- запуск сравнения;
- запуск генерации выжимки и теста.

### 4.2. Ответственное лицо
Отвечает за:

- просмотр сгенерированного теста;
- утверждение теста перед выдачей сотрудникам.

### 4.3. Сотрудник
Отвечает за:

- прохождение теста;
- указание ФИО;
- получение результата.

## 5. Must have для MVP

В MVP обязательно должны входить:

- загрузка документов;
- загрузка новых версий документов;
- парсинг DOCX / PDF / TXT;
- разбиение на статьи / пункты / подпункты;
- сравнение версий;
- выявление изменений;
- краткая выжимка;
- генерация теста;
- утверждение теста ответственным лицом;
- прохождение теста сотрудником с указанием ФИО;
- сохранение результатов;
- отчёты;
- стабильный запуск;
- автотесты.

## 6. Nice to have / можно отложить

Следующие функции допустимы, но не обязательны для первой защищаемой версии:

- чат по документам;
- семантический поиск по фрагментам;
- сложные LLM-сценарии;
- тяжёлые внешние интеграции;
- развитая ролевая модель;
- сложные личные кабинеты;
- расширенная аналитика;
- импорт больших внешних массивов нормативных документов.

## 7. Out of scope для MVP

За пределами MVP находятся:

- универсальный юридический помощник;
- полный поиск “по всем законам”;
- корпоративная LMS-платформа;
- кадровая система;
- документооборот организации в целом;
- сложные интеграции с множеством внешних систем;
- мобильное приложение.

## 8. Граница MVP

MVP считается корректно определённым, если в нём можно показать один цельный живой сценарий:

1. загрузить документ;
2. загрузить новую редакцию;
3. сравнить версии;
4. показать изменения;
5. показать краткую выжимку;
6. сгенерировать тест;
7. утвердить тест;
8. пройти тест от имени сотрудника;
9. показать результат и отчёт.

Если функция не усиливает этот сценарий, она не должна попадать в MVP автоматически.

## 9. Критерии успеха MVP

MVP успешен, если:

- демонстрация проходит без ручных “костылей”;
- пользователь может понять, что именно изменилось;
- тест строится на реальных изменениях;
- результаты прохождения сохраняются;
- отчёт по сотруднику или тесту можно показать комиссии;
- система запускается локально стабильно;
- код покрыт базовыми автотестами.

## 10. Текущее состояние архива относительно scope

На момент аудита в коде уже частично есть:

- документы и версии;
- извлечение текста из TXT и DOCX;
- сравнение версий;
- краткая выжимка;
- генерация теста;
- прохождение теста;
- сохранение попыток;
- автотесты.

На момент аудита ещё отсутствуют или недоведены до MVP:

- PDF-парсинг;
- workflow утверждения теста;
- полноценные отчёты как пользовательская функция;
- минимальный завершённый UI.

## 11. Правило управления scope

Приоритет всегда у функций, которые:

- усиливают основной сценарий;
- повышают качество демонстрации;
- помогают защите магистерского проекта;
- дают прикладную ценность для МФЦ.

Любые функции, которые уводят проект в сторону от этой цели, должны откладываться.
