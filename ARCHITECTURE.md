# ARCHITECTURE

## 1. Назначение документа

Документ фиксирует архитектурные принципы проекта и должен оставаться согласованным с кодом, README и scope.

Цель архитектуры — удержать проект в рамках прикладной системы анализа изменений в документах, а не превратить его в расплывчатую AI-платформу.

## 2. Архитектурный фокус

Главный объект системы — **один документ и его версии**.

Главный процесс системы:

1. загрузить документ;
2. загрузить новую редакцию;
3. извлечь текст;
4. разбить текст на структурные фрагменты;
5. сравнить две версии;
6. выделить изменения;
7. сформировать краткую выжимку;
8. сгенерировать квиз;
9. утвердить квиз;
10. дать сотруднику пройти квиз;
11. сохранить результаты и показать отчёт.

## 3. Архитектурные принципы

### 3.1. Version-first, а не chat-first

Проект строится вокруг сравнения редакций одного документа.

Неправильный центр тяжести для MVP:
- универсальный чат по законам;
- агентная платформа;
- поиск как самостоятельная цель;
- AI как единственный источник логики.

### 3.2. Local-first и demo-ready

Система должна запускаться на одном ПК и быть пригодной для устойчивой демонстрации.

Это означает:
- простое локальное развёртывание;
- понятный путь запуска без обязательного облака;
- минимальное число внешних обязательных сервисов.

### 3.3. Backend-first

Основная логика находится в backend:
- хранение документов и версий;
- извлечение текста;
- разбиение на чанки;
- diff;
- rule-based enrichment;
- brief;
- quiz generation;
- approval;
- attempts и reports.

UI остаётся тонким слоем представления на Django templates.

### 3.4. Deterministic / hybrid first

Базовая бизнес-логика не должна зависеть исключительно от LLM.

Надёжный контур проекта строится на:
- явных моделях данных;
- детерминированном сравнении;
- rule-based классификации и enrichment;
- воспроизводимом тестовом поведении.

LLM, embeddings и semantic search допустимы только как усиливающий слой.

### 3.5. Explainability важнее «магии»

Для магистерского проекта и прикладного использования важно объяснить:
- какие версии сравнивались;
- какие фрагменты изменились;
- почему изменение сочтено важным;
- на каких изменениях основан квиз;
- как посчитан результат попытки.

### 3.6. Явные границы слоёв внутри backend

Для app `documents` принят практический, а не академический вариант разбиения:

- `domain/` — детерминированная предметная логика сравнения редакций, enrichment, summary и quiz generation;
- `services/` — orchestration и интеграции: ingestion, importance analysis, optional search/Qdrant, evaluation services;
- `api/` — HTTP/DRF слой: serializers, endpoints, viewsets, url routing;
- `demo/` — демонстрационный presentation-слой и demo corpus;
- `models.py` — единая ORM-модель данных MVP.

Это разбиение выбрано как компромисс между читаемостью и устойчивостью:

- без переусложнения отдельными микросервисами или десятками Django apps;
- без смешения demo/UI, API и доменного ядра в одном плоском каталоге;
- с сохранением понятного пути роста к следующим фазам проекта.

## 4. Логические подсистемы

На уровне структуры репозитория эти подсистемы теперь отражаются напрямую в каталогах `backend/documents/domain`, `backend/documents/services`, `backend/documents/api` и `backend/documents/demo`.


### 4.1. Хранение документов

Отвечает за:
- карточки документов;
- версии документов;
- файлы и извлечённый текст;
- нормализованный текст.

### 4.2. Ingestion и структурирование

Отвечает за:
- TXT / DOCX / PDF с текстовым слоем;
- нормализацию;
- построение чанков.

Ограничение текущей версии: **OCR для сканированных PDF не входит в текущий контур**.

### 4.3. Сравнение версий

Отвечает за:
- matching чанков;
- added / removed / modified / moved;
- similarity-based сопоставление;
- текстовый diff;
- классификацию изменений.

### 4.4. Разъяснения и значимость изменений

Отвечает за:
- краткую выжимку по diff;
- rule-based признаки значимости;
- подготовку материала для пользователя и квиза.

### 4.5. Подсистема тестирования

Отвечает за:
- генерацию квиза;
- хранение payload квиза;
- approval workflow;
- прохождение сотрудником;
- фиксацию score и ответов.

### 4.6. Отчётность

Отвечает за:
- список попыток;
- score / total;
- просмотр результата конкретной попытки;
- demo-ready отчёт по квизу.

## 5. Технологическая схема

Минимальная схема текущего проекта:

- Backend: Django + Django REST Framework
- UI: Django templates
- Локальная разработка и тесты: SQLite
- Docker Compose path: PostgreSQL
- Файлы: локальное файловое хранилище
- Поиск: опционально Qdrant
- AI-слой: rule-based / hybrid / optional LLM enhancements

## 6. Что реально реализовано в текущем коде

В коде уже есть:
- доменные модели документов, версий, чанков, квизов и попыток;
- ingestion pipeline;
- compare API;
- brief API;
- quiz save / approve / attempt / report flow;
- demo UI;
- demo corpus;
- backend test suite.

Важно: часть более богатой доменной модели уже существует в ORM, но реальный рабочий runtime-контур в нескольких сценариях опирается на JSON payload внутри `GeneratedQuiz` и `QuizAttempt`. Это допустимо для текущего MVP, но должно описываться честно.

## 7. Что считается опциональным слоем

Не является обязательной частью MVP-ядра:
- Qdrant и semantic search;
- embeddings;
- LLM-based enrichment;
- расширенная аналитика;
- сложная auth / roles система.

## 8. Архитектурные ограничения

В рамках текущего контура не делаем:
- микросервисную архитектуру;
- тяжёлую распределённую инфраструктуру;
- LangGraph / multi-agent как основу проекта;
- отдельный SPA frontend;
- сложную корпоративную IAM/RBAC платформу.

## 9. Критерий архитектурной корректности

Новое решение считается уместным, если оно:
- усиливает сценарий «предыдущая редакция vs новая редакция»;
- повышает воспроизводимость;
- повышает demo-устойчивость;
- улучшает объяснимость результатов;
- не перегружает проект ради внешней технологической моды.
