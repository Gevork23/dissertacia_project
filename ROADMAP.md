# ROADMAP

## Общая логика проекта

Проект развивается не как набор разрозненных AI-функций, а как прикладная система с маршрутом:

**документ → версии → изменения → выжимка → тест → утверждение → прохождение → отчёт**

Ниже зафиксированы **функциональные фазы продукта**. Отдельно от них в текущей работе используется **инженерный этап стабилизации**, который в магистерском процессе удобно называть «Фаза 1: полировка и приведение проекта в порядок».

---

## Функциональная фаза 0. Фиксация замысла проекта

### Цель
Убрать терминологический и продуктовый туман.

### Что должно быть на выходе
- единая формулировка проекта;
- главный сценарий;
- границы MVP;
- архитектурные принципы;
- согласованная документация.

### Definition of Done
- документы не противоречат друг другу;
- проект можно кратко и одинаково объяснить;
- понятно, что входит в MVP, а что отложено.

---

## Функциональная фаза 1. Документы, версии, ingestion

### Цель
Сделать устойчивую основу хранения и обработки документов.

### Что включено
- модели документов и версий;
- загрузка файлов;
- TXT / DOCX / PDF с текстовым слоем;
- извлечение текста;
- нормализация;
- построение чанков.

### Definition of Done
- можно загрузить документ и новую редакцию;
- текст извлекается воспроизводимо;
- чанки строятся автоматически;
- ingestion покрыт тестами.

---

## Функциональная фаза 2. Сравнение редакций

### Цель
Сделать объяснимое сравнение двух версий одного документа.

### Что включено
- diff по структурным фрагментам;
- added / removed / modified / moved;
- rule-based выделение значимых изменений;
- формирование текстового diff.

### Definition of Done
- система сравнивает две версии корректно;
- результат пригоден для brief и quiz;
- ключевые сценарии покрыты тестами.

---

## Функциональная фаза 3. Выжимка и генерация теста

### Цель
Сделать из diff понятный обучающий артефакт.

### Что включено
- краткая выжимка по изменениям;
- генерация вопросов по diff;
- сохранение квиза;
- подготовка к approval workflow.

### Definition of Done
- brief и quiz строятся по реальным изменениям;
- квиз можно сохранить и показать;
- поведение покрыто тестами.

---

## Функциональная фаза 4. Утверждение, прохождение, результаты

### Цель
Замкнуть прикладной контур использования.

### Что включено
- утверждение квиза ответственным лицом;
- прохождение сотрудником;
- сохранение результатов;
- просмотр отчёта.

### Definition of Done
- черновик нельзя выдавать без approval;
- сотрудник может пройти утверждённый квиз;
- попытки и результаты сохраняются.

---

## Функциональная фаза 5. Демонстрационный MVP

### Цель
Собрать устойчивый сценарий показа на одном ПК.

### Что включено
- demo UI на Django templates;
- demo corpus;
- команда подготовки демонстрационных данных;
- локальный запуск и smoke-проверки.

### Definition of Done
- demo можно запустить без ручной правки кода;
- сценарий показа воспроизводим;
- стек не перегружен лишними зависимостями.

---

## Функциональная фаза 6. Подготовка к защите

### Цель
Довести проект до состояния сильной и честной защиты.

### Что включено
- финальная терминология;
- согласование README / scope / architecture / roadmap;
- demo-script;
- ERD и поясняющие материалы;
- контрольный прогон сценария.

### Definition of Done
- документация согласована с кодом;
- можно честно обозначить реальные границы MVP;
- проект удобно демонстрировать комиссии.

---

## Текущий инженерный этап: стабилизация и полировка

Этот этап не добавляет крупную новую функциональность. Его цель:

- проаудировать текущее состояние;
- убрать противоречия между кодом, тестами и документами;
- стабилизировать запуск;
- очистить репозиторий от мусора;
- зафиксировать реальный demo-ready MVP scope.

Именно этот этап является текущей «Фазой 1» в рабочем процессе магистерского проекта.
