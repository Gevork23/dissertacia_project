# PROJECT_SCOPE

## 1. Цель проекта

Создать интеллектуальную систему анализа нормативно-правовых и внутренних регламентных документов, которая помогает быстро объяснять сотрудникам, что изменилось в новой редакции документа, и проверять усвоение изменений через тестирование.

## 2. Основной прикладной сценарий

Главный сценарий проекта:

**документ → версии → изменения → выжимка → генерация теста → утверждение → прохождение → отчёт**

Это и есть ядро MVP.

## 3. Основной режим анализа

Основной режим анализа:

**сравнение новой редакции документа с предыдущей редакцией того же документа**

Проект не должен терять этот фокус.

## 4. Пользовательские роли текущего MVP

В текущем MVP роли задаются скорее сценарно, чем через полноценную auth-модель:

### 4.1. Администратор / оператор
Отвечает за:
- загрузку документа;
- загрузку новых редакций;
- запуск сравнения;
- генерацию brief и quiz.

### 4.2. Ответственное лицо
Отвечает за:
- просмотр сгенерированного квиза;
- утверждение квиза перед выдачей сотрудникам.

### 4.3. Сотрудник
Отвечает за:
- прохождение квиза;
- указание ФИО;
- получение результата.

## 5. Must have для demo-ready MVP

В обязательный контур входят:
- загрузка документов и новых версий;
- парсинг TXT / DOCX / PDF с текстовым слоем;
- построение чанков;
- compare версий;
- выделение изменений;
- краткая выжимка;
- генерация квиза;
- approval workflow;
- прохождение квиза сотрудником с указанием ФИО;
- сохранение результатов;
- просмотр отчёта;
- стабильный локальный запуск;
- базовые автотесты.

## 6. Nice to have / можно отложить

Следующие функции допустимы, но не обязательны для текущей защищаемой версии:
- OCR для сканов;
- семантический поиск;
- сложные LLM-сценарии;
- тяжёлые внешние интеграции;
- развитая ролевая модель;
- личные кабинеты;
- расширенная аналитика;
- импорт больших внешних массивов документов.

## 7. Out of scope

За пределами текущего MVP находятся:
- универсальный юридический помощник;
- полный поиск по всем законам РФ;
- агентная оркестрация как основа продукта;
- корпоративная LMS-платформа общего назначения;
- мобильное приложение;
- сложная enterprise-инфраструктура.

## 8. Граница MVP

MVP считается определённым корректно, если можно показать один цельный сценарий:

1. загрузить документ;
2. загрузить новую версию;
3. сравнить версии;
4. показать изменения;
5. показать brief;
6. сгенерировать квиз;
7. утвердить его;
8. пройти квиз от имени сотрудника;
9. показать результат и отчёт.

## 9. Критерии успеха MVP

MVP успешен, если:
- демонстрация проходит без ручных подправлений кода;
- пользователь видит, что именно изменилось;
- квиз строится на реальных изменениях;
- попытки сохраняются;
- отчёт можно показать комиссии;
- система стабильно запускается локально;
- тестовый контур отражает реальное поведение системы.

## 10. Текущее состояние архива относительно scope

На момент аудита в коде уже есть:
- документы и версии;
- ingestion pipeline;
- compare;
- brief;
- quiz generation;
- approval;
- attempts;
- report view;
- demo UI;
- demo corpus;
- backend tests.

Нужно проговаривать честно:
- PDF поддерживается без OCR;
- demo UI — это демонстрационный, а не полноценный продуктовый интерфейс;
- поиск с Qdrant — опциональная возможность;
- роли пока не проведены через полноценную auth-систему.

## 11. Правило управления scope

Приоритет у функций, которые:
- усиливают основной сценарий;
- повышают устойчивость демонстрации;
- помогают защите магистерского проекта;
- увеличивают объяснимость и воспроизводимость результата.

Функции, которые уводят проект в сторону, не должны автоматически попадать в текущий MVP.
