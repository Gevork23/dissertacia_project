# ARCHITECTURE

## 1. Назначение архитектуры

Этот документ фиксирует не детальную реализацию по классам и модулям, а **архитектурные принципы проекта**, которые не должны противоречить ни коду, ни README, ни roadmap.

Цель архитектуры — удержать проект в рамках прикладной системы анализа редакций нормативно-правовых документов, а не превратить его в расплывчатую “AI-платформу”.

## 2. Архитектурный фокус проекта

Главный объект системы — **один нормативно-правовой документ и его версии**.

Главный процесс системы:

1. загрузить документ;
2. загрузить новую редакцию;
3. извлечь текст;
4. разбить текст на структурные фрагменты;
5. сравнить две версии одного документа;
6. выделить значимые изменения;
7. сформировать краткое разъяснение;
8. сгенерировать тест;
9. утвердить тест ответственным лицом;
10. дать сотруднику пройти тест;
11. сохранить результаты и показать отчёт.

## 3. Архитектурные принципы

### 3.1. Version-first, а не chat-first

Проект строится вокруг сравнения версий одного документа.

Правильный вопрос для системы:

- “Чем новая редакция отличается от предыдущей?”
- “Что изменилось для сотрудников?”
- “Как быстро проверить, что сотрудники поняли изменения?”

Неправильный фокус для MVP:

- “сделаем чат по всем законам”
- “сделаем универсального AI-юриста”
- “сначала сделаем поиск, а потом подумаем о прикладном сценарии”

### 3.2. Локальное развёртывание

Система должна запускаться на одном ПК и быть доступной по сети внутри локального окружения.

Это означает:

- backend и база данных разворачиваются локально;
- интерфейс должен открываться по локальному адресу;
- демонстрация должна быть воспроизводимой без сложной инфраструктуры.

### 3.3. Тонкий интерфейс, сильный backend

Основная логика должна находиться в backend:

- хранение документов и версий;
- извлечение текста;
- разбиение на структуру;
- сравнение;
- классификация изменений;
- выжимка;
- генерация тестов;
- сохранение попыток и отчётов.

UI должен быть минимальным и демонстрационным, а не тяжёлым продуктовым фронтендом.

### 3.4. AI — вспомогательный слой, а не центр системы

LLM, rule-based анализ, гибридное извлечение сущностей, semantic search и подобные компоненты допустимы только в той мере, в какой они усиливают основной сценарий:

- делают выжимку понятнее;
- помогают выделить важные изменения;
- улучшают качество тестовых заданий.

Они не должны подменять базовую прикладную логику.

### 3.5. Объяснимость важнее “магии”

Для магистерского проекта и прикладного инструмента важно, чтобы результат можно было объяснить:

- какая версия с чем сравнивалась;
- какой фрагмент изменился;
- почему изменение признано важным;
- по каким изменениям был построен тест;
- как получен итоговый результат сотрудника.

## 4. Логические подсистемы

## 4.1. Подсистема хранения документов

Отвечает за:

- карточку документа;
- версии документа;
- привязку загруженных файлов;
- хранение исходного и нормализованного текста.

## 4.2. Подсистема извлечения и структурирования текста

Отвечает за:

- поддержку DOCX / PDF / TXT;
- нормализацию текста;
- разбиение на статьи / пункты / подпункты;
- формирование структурных фрагментов для сравнения.

## 4.3. Подсистема сравнения версий

Отвечает за:

- выбор двух версий одного документа;
- сопоставление фрагментов;
- выявление added / removed / modified / moved;
- выделение содержательно значимых изменений.

## 4.4. Подсистема разъяснений

Отвечает за:

- краткую выжимку по изменениям;
- человеческое описание того, что поменялось;
- фокус на последствиях для сотрудника.

## 4.5. Подсистема тестирования знаний

Отвечает за:

- генерацию теста по изменениям;
- хранение теста;
- утверждение теста ответственным лицом;
- прохождение теста сотрудником;
- хранение результатов.

## 4.6. Подсистема отчётности

Отвечает за:

- список попыток;
- баллы;
- процент правильных ответов;
- сводный просмотр результатов по тесту и сотрудникам.

## 5. Технологическая схема MVP

Рекомендуемая минимальная технологическая схема:

- Backend: Django + Django REST Framework
- База данных: PostgreSQL
- Хранение файлов: локальное файловое хранилище
- UI: минимальный веб-интерфейс
- AI-компоненты: rule-based / hybrid / LLM как вспомогательные модули
- Дополнительный поиск: опционально, не как основа MVP

## 6. Что уже есть в текущем архиве

В текущем архиве уже есть backend-прототип, который покрывает часть архитектуры:

- документы и версии;
- чанки;
- diff;
- brief;
- quiz generation;
- quiz attempts;
- demo corpus;
- автотесты;
- docker-compose.

## 7. Что ещё должно появиться до целевого MVP

До целевого MVP необходимо довести:

- поддержку PDF;
- утверждение теста ответственным лицом;
- полноценную пользовательскую отчётность;
- минимальный демонстрационный UI;
- согласованную документацию;
- финальные критерии стабильности запуска.

## 8. Архитектурные ограничения

В рамках MVP не делаем:

- тяжёлую распределённую архитектуру;
- микросервисы;
- сложную RBAC-систему;
- кабинетную платформу с большим количеством ролей;
- чат-бот как центральную сущность проекта;
- интеграции, без которых можно защитить и показать проект.

## 9. Критерий архитектурной правильности

Любое новое решение считается архитектурно корректным, если оно:

- усиливает сценарий “новая редакция vs предыдущая редакция”;
- упрощает демонстрацию;
- повышает воспроизводимость;
- улучшает объяснимость результатов;
- не размывает MVP лишними возможностями.
